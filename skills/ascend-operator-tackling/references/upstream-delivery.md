# 上游交付与 PR 纪律

## 目标

让最终交付能被独立维护者理解、复现、评审和长期演进，而不是把攻坚现场的实验状态直接推给上游。

## 分支和所有权

- 上游基线只读；
- 集成分支唯一；
- 实验分支短生命周期；
- 每个候选有明确 owner、证据和回退点；
- 合并只从已通过 gate 的候选进入集成分支。

## 生产与实验隔离

生产代码不得包含：

- 实验环境开关；
- `/tmp` dump；
- 调试打印和硬编码路径；
- `.orig`、`.bak`、临时 patch；
- 未接线 kernel；
- 仅为单个 benchmark shape 增加的白名单；
- 未使用或已否定 route。

实验代码放在独立 worktree/目录，保留失败证据，但不进入交付 diff。

## 文件设计

优先形成：

- 公共 API/类型；
- host dispatch/route table；
- 公共 layout/copy primitive；
- 稳定的计算 primitive；
- 目标独立 kernel；
- tiling/config；
- 测试与 README。

避免：

- 一个 host if-chain 承载多套不兼容协议；
- 为每个 shape 写独立入口；
- 大小内核复制同一逻辑；
- 生产路径依赖探针文件。

分区间可以存在，但边界应由资源模型、UB/L1 容量、batch 规模或语义决定，而不是测试编号。

## 提交拆分

一个提交只做一个逻辑变更：

1. 接口/类型；
2. 基础实现；
3. 正确性修复；
4. 公共 primitive；
5. route/调度；
6. 测试与文档；
7. 清理。

不要混合格式化、无关重构、性能改动和平台兼容。

## 依赖与兼容

- 使用目标仓库已有依赖和公共设施；
- 新增依赖必须有明确收益和可见影响；
- 不把测试专用依赖加入生产库；
- 不假定固定 CANN/硬件，优先能力检测；
- 对不支持组合返回正确状态或走安全 fallback；
- 版本宏和兼容层应集中管理，不散落在 kernel。

## 随代码提交的证据

至少包括：

- 构建命令和结果；
- 完整正确性测试；
- 目标性能测试；
- 关键回归测试；
- 原始日志/结果路径；
- 源码和二进制 hash；
- 已知限制和未覆盖场景。

报告中的每个关键结论都要链接到 raw evidence。

## 交付前检查

1. 工作树干净或 dirty diff 完整可重建；
2. `git status --porcelain` 只剩预期文件；
3. diff 只包含目标变更；
4. 无敏感信息；
5. 无未接线/实验代码；
6. 构建从干净状态可重复；
7. 全量正确性通过；
8. 目标性能口径通过；
9. Reviewer 已独立验证；
10. README、测试说明和恢复命令完整；
11. 失败家族与已知限制已记录；
12. 新 agent 能按 HANDOFF 从头复现。

## 上游评审关注点

预期 Reviewer 会检查：

- 接口是否一致；
- 边界和 fallback 是否完整；
- 是否引入不必要依赖；
- 是否有针对特定输入的隐藏 shortcut；
- 测试是否覆盖真实分布；
- 性能是否在干净构建和目标环境复现；
- 路由是否可维护；
- 是否存在跨平台/版本风险；
- 是否有证据证明通过而不是“作者相信”。
