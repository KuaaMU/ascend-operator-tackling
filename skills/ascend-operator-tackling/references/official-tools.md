# 官方工具发现与使用

## 原则

工具名称和参数会随 CANN、系统镜像和芯片变化。不要硬编码旧命令或假设工具存在。
先运行 `scripts/discover_environment.py`，再从当前安装的文档、`--help`、头文件和样例确认语义。

工具输出是原始证据。任何摘要都要能回到完整日志。

## 发现顺序

1. 运行系统、编译器和构建工具版本；
2. CANN/Ascend 环境变量和安装根目录；
3. profiling、logging、sanitizer、debugger、compiler 工具是否可用；
4. 设备节点、驱动状态和空闲情况；
5. 当前仓库编译/测试入口；
6. 官方文档和样例是否与当前版本匹配。

## 工具职责

### Profiling

用于回答：

- 总时间由哪些 kernel/task 组成；
- 每个阶段占多少；
- compute、memory、scalar、vector、fixpipe、MTE、launch gap 的比例；
- 是否存在 cache miss、pipeline idle、同步或 occupancy 问题。

不要只看总 duration。至少记录：

- 过滤到哪些 kernel/task；
- 采样数、采样范围、warmup；
- device time 与 host/wall time 的区别；
- 路由和输入版本；
- 同会话前后对照。

### Logging / Error Decode

用于：

- 解码 driver/runtime/compiler 错误；
- 定位故障 kernel、地址、流水和对齐问题；
- 区分参数错误、资源错误、越界和同步问题。

先保存原始错误码和设备上下文，再搜索文档或代码中的对应定义。

### Sanitizer / Race / Sync Check

用于：

- 越界、未初始化、use-after-free；
- 线程或流水竞争；
- 缺失同步和不合法依赖；
- 非确定性错误的机制定位。

若工具需要特殊编译选项，记录“诊断构建”和“生产构建”的差异。诊断通过不等于生产正确，
但诊断报错在无法解释前不能 promote。

### Debugger / Dump

用于：

- 确定真实中间值与参考值的偏差；
- 检查 layout、stride、索引、尾块和 padding；
- 比较两个理论等价实现的中间结果。

Dump 必须带 case、阶段、shape、路由、地址/偏移和版本信息。大文件不要进入交付树。

### Compiler Diagnostics

用于：

- 判断常量折叠、寄存器压力、代码尺寸、内联和指令生成；
- 解释“源码看起来相同，device 行为不同”；
- 发现未定义行为、对齐假设或资源上限。

当编译器诊断与运行时结论冲突时，以目标设备行为为准，同时保留两边证据。

### Correctness Tools

用于：

- 按目标语义生成参考结果；
- 检查边界、异常值、奇异/退化输入；
- 比较不同 fast/fallback route。

测试应覆盖目标分布和对抗分布。不能因为 benchmark 输入具有某种结构，就把该结构当作完整语义。

## 官方文档与源码

版本优先级：

1. 当前安装头文件、样例、帮助和本地文档；
2. 与当前 CANN 版本对应的官方在线文档；
3. 官方仓库源码和 issue/PR；
4. 任务书或测试包；
5. 二手文章和历史总结。

记录 URL/路径、版本、日期和核对时间。版本不明确的外部资料只能作为假设。

## 自建 Probe

自建 probe 用于解释官方工具结果或区分假设，不替代官方 gate。

每个 probe 应：

- 只改一个变量；
- 有对照组；
- 直接测关键路径，而不是无关总量；
- 明确 floor 和噪声；
- 在结果出来前写 kill criterion；
- 在失败后回退并保留证据。

## 工具不可用

若工具缺失或版本不兼容：

1. 记录缺失事实和影响范围；
2. 尝试当前环境支持的等价官方能力；
3. 若无等价能力，使用最低风险的过程证据缩小假设；
4. 在最终结论中明确未验证风险；
5. 不要用外部环境的数字替代目标环境验收。
